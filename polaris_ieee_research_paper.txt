# POLARIS: A Hybrid AI-Powered Digital Well-Being, Adaptive Learning, and Ethical Parental Control Platform

**Source Document for IEEE-Format Research Paper**

---

## ABSTRACT

The proliferation of digital devices among students has introduced dual-edged consequences: unprecedented access to educational resources alongside equally unprecedented exposure to distraction vectors. Existing digital well-being solutions operate in isolation—browser extensions merely block websites, learning management systems track grades without behavioral context, and parental controls impose blanket restrictions without semantic understanding of content. This paper presents **POLARIS** (Productivity-Oriented Learning Analytics and Real-time Intelligent System), a novel, multi-component platform that unifies real-time behavioral telemetry, AI-driven content classification, adaptive learning orchestration, and ethically-constrained parental oversight into a single cohesive system. POLARIS introduces several contributions to the field: (1) a **dual-layer tracking architecture** that monitors both browser-based and native desktop application usage without mutual interference through a deduplication protocol; (2) a **semantic video classification engine** powered by sentence-transformer embeddings (all-MiniLM-L6-v2, 384-dimensional) that distinguishes educational YouTube content from entertainment with cosine similarity thresholds (≥0.75 for auto-match, ≥0.65 for candidate confirmation); (3) an **adaptive learning pipeline** that generates personalized study plans with AI-curated YouTube chapters, automatically tracks video watch progress at sub-second granularity, and gates assessment quizzes behind verified completion; (4) a **LearnerProfile knowledge graph** that persists mastered topics and weak areas across study plans to enable cross-plan curriculum personalization; (5) a **privacy-preserving data architecture** that strips all URLs to hostname-only format before storage and enforces a sensitive-domain blocklist; and (6) a **Polaris Lab**, an in-browser coding IDE with sandboxed server-side Python execution and automated test-case verification. The system architecture employs a Chrome Extension (Manifest V3) for client-side telemetry, a Python desktop tracker for native application monitoring, a FastAPI backend with MySQL persistence, WebSocket-based real-time communication for blocking rule propagation, and a React dashboard for visualization. POLARIS demonstrates that intelligent, context-aware behavioral analytics can coexist with privacy preservation and ethical oversight, providing a foundational framework for the next generation of digital well-being platforms.

**Keywords:** Digital Well-Being, Adaptive Learning, Natural Language Processing, Sentence Embeddings, Browser Extension, Parental Control, Productivity Analytics, Real-Time Tracking, Ethical AI, Code Execution Sandbox

## I. INTRODUCTION

### A. Problem Statement and Motivation

The accelerating digitization of education has created a paradox for learners: the same devices that provide access to Khan Academy lectures, Stack Overflow solutions, and Coursera courses also serve as conduits to Instagram, TikTok, and gaming platforms. A 2023 study by Common Sense Media reported that adolescents spend an average of 8 hours and 39 minutes daily on screens, with educational activity constituting less than 20% of this total [1]. The challenge is not merely one of time management; it is fundamentally a classification problem—the same platform (e.g., YouTube) can host both an advanced algorithms lecture and a viral entertainment clip, yet existing tools treat the entire domain uniformly.

Contemporary solutions to this problem suffer from three critical limitations:

1. **Binary Classification Failure.** Traditional website blockers and parental controls operate on domain-level blacklists or whitelists, treating `youtube.com` as either entirely productive or entirely distracting. This approach is fundamentally incompatible with mixed-use platforms where educational and entertainment content coexist under the same domain.

2. **Siloed Architecture.** Existing productivity tools (e.g., RescueTime, Toggl) track time but do not influence learning outcomes; learning management systems (e.g., Moodle, Canvas) manage curricula but lack behavioral telemetry; parental controls (e.g., Net Nanny, Qustodio) restrict access but provide no educational value. The absence of a unified platform creates data silos that prevent holistic well-being optimization.

3. **Static Content Classification.** Most systems rely on manually curated category databases that cannot adapt to emerging content. A new educational channel on YouTube, a recently published coding tutorial, or a novel AI-assisted learning tool would remain unclassified until a human administrator updates the ruleset.

### B. Research Objectives

This research addresses these limitations through the design, implementation, and analysis of POLARIS, a system with the following objectives:

- **RO1:** Design a multi-modal tracking architecture capable of monitoring both browser-based and native desktop application activity without duplicate counting.
- **RO2:** Implement a semantic content classification engine that distinguishes educational from entertainment content within mixed-use platforms at the individual video/page level.
- **RO3:** Develop an adaptive learning pipeline that generates personalized curricula, automatically tracks progress against assigned content, and adapts difficulty based on assessment performance.
- **RO4:** Construct a privacy-preserving data pipeline that ensures no sensitive information (full URLs, search queries, chat content) is ever stored or transmitted.
- **RO5:** Build an ethical parental oversight module that provides aggregate behavioral insights without exposing individual video titles, search histories, or private communications.
- **RO6:** Provide an integrated coding environment (Lab) that enables students to practice programming exercises generated alongside study plan chapters, with server-side sandboxed execution and automated verification.

### C. Contributions

POLARIS makes the following contributions to the digital well-being and educational technology literature:

1. **Dual-Layer Deduplication Protocol.** A novel architecture where the desktop tracker explicitly yields to the browser extension for all browser-based activity, preventing the double-counting that plagues existing hybrid tracking systems. The desktop tracker identifies browser processes (e.g., `chrome.exe`, `msedge.exe`, `firefox.exe`, `brave.exe`) via a curated set and classifies them as "neutral," delegating fine-grained per-site tracking entirely to the Chrome extension.

2. **Three-Tier YouTube Classification Cascade.** A hierarchical content classification system that evaluates: (a) real-time NLP semantic matching via sentence-transformer embeddings as the highest-priority signal, (b) keyword-based title analysis as a secondary fallback, and (c) domain-level defaults as the baseline.

3. **Cross-Plan Learner Profile.** A persistent knowledge graph (`LearnerProfile` model) that accumulates mastered topics, weak areas, and rolling quiz score averages across multiple study plans. Subsequent plan generation injects this profile context into the LLM prompt, enabling the system to skip already-mastered fundamentals and add depth on identified weaknesses.

4. **Shadow DOM Anti-Circumvention Overlay.** A blocking overlay implementation that uses the Shadow DOM API with a `MutationObserver` anti-removal watcher to ensure the block cannot be dismissed by user-initiated DOM manipulation or browser developer tools.

5. **Privacy-First Data Architecture.** A dual-layer privacy filter (client-side `privacyFilter.js` and server-side `privacy.py`) that strips URLs to hostnames before any network transmission and enforces field-level truncation matching backend Pydantic schema constraints (domain: 255 chars, page_title: 500 chars, yt_classification: 20 chars).

## II. RELATED WORK

### A. Digital Well-Being and Productivity Tracking

The concept of digital well-being has evolved from simple screen-time measurement to nuanced behavioral analytics. Kim et al. [2] introduced the notion of "digital flourishing," arguing that mere time-on-device metrics are insufficient and that the quality of digital engagement must be evaluated. RescueTime, one of the earliest commercial productivity trackers, classifies websites into five productivity tiers but relies entirely on a manually curated database, making it unable to handle mixed-use platforms [3].

Apple's Screen Time and Google's Digital Wellbeing represent platform-level implementations that provide aggregate usage statistics but lack the granularity to distinguish between an educational YouTube video and entertainment content on the same platform [4]. These tools also operate in isolation from learning outcomes, providing no mechanism to correlate usage patterns with academic performance.

### B. Adaptive Learning Systems

Adaptive learning has a rich history in educational technology, from early intelligent tutoring systems (ITS) to modern AI-powered platforms. Knewton's adaptive learning engine pioneered the use of knowledge graphs for personalized learning paths, adjusting content difficulty based on student performance [5]. More recently, Duolingo's Half-Life Regression model demonstrated the effectiveness of spaced repetition algorithms in language learning [6].

However, existing adaptive learning systems operate within closed ecosystems—they generate and serve their own content. POLARIS departs from this model by curating external content (YouTube videos) and building adaptive curricula around open-source educational material. This approach is inspired by the work of Guo et al. [7], who demonstrated that shorter, informal videos (characteristic of YouTube educational content) produce higher engagement than traditional lecture recordings.

### C. Content Classification Using NLP

The application of natural language processing to content classification has advanced significantly with the advent of transformer-based models. Devlin et al. [8] introduced BERT, which demonstrated that pre-trained language representations could achieve state-of-the-art results on downstream classification tasks. Reimers and Gurevych [9] extended this work with Sentence-BERT (SBERT), producing semantically meaningful sentence embeddings suitable for cosine similarity comparison.

POLARIS leverages the all-MiniLM-L6-v2 model from the SBERT family, which produces 384-dimensional embeddings optimized for semantic textual similarity. This model was selected for its balance between accuracy and inference speed, as it must operate in real-time during video playback classification.

### D. Parental Control and Ethical Oversight

Parental control systems have traditionally operated on a surveillance paradigm, monitoring and restricting children's digital activity with minimal transparency [10]. Wisniewski et al. [11] critiqued this approach, arguing that surveillance-based parental controls undermine adolescent autonomy and fail to develop self-regulation skills. The "Cluster-N-Engage" framework proposed by Alharbi et al. [12] introduced the concept of clustering-based behavioral analysis for parental insights, providing aggregate behavioral patterns rather than individual action logs.

POLARIS draws inspiration from this ethical oversight paradigm, implementing a system where parents receive productivity scores, focus factors, and domain-level time breakdowns without access to specific video titles, search queries, or chat content. The system explicitly filters sensitive domains (e.g., `mail.google.com`, `web.whatsapp.com`, `discord.com`) from parental view, ensuring that personal communications remain private even in a monitored environment.

### E. Browser Extension Architecture

The evolution from Chrome's Manifest V2 to Manifest V3 introduced significant architectural constraints. Service workers replaced persistent background pages, creating challenges for long-running processes such as continuous activity tracking [13]. Manifest V3 also introduced the `declarativeNetRequest` API as a replacement for the more flexible `webRequest` API, fundamentally changing how browser extensions implement content blocking.

POLARIS addresses these constraints through several engineering techniques: `chrome.alarms` for periodic service worker wake-up, `chrome.storage.local` for state persistence across service worker sleep/wake cycles, and an offline queue (`tracking_queue`) for data buffering during network unavailability.

### F. Coding Practice Environments

Interactive coding environments have become integral to computer science education. Platforms such as LeetCode, HackerRank, and Replit provide browser-based coding with automated testing [14]. POLARIS contributes to this space by embedding a coding lab directly within the learning flow, linking coding tasks to specific study plan chapters and providing sandboxed server-side Python execution alongside client-side JavaScript execution.

## III. SYSTEM ARCHITECTURE

### A. Architectural Overview

POLARIS employs a multi-tier, event-driven architecture comprising five principal components:

1. **Chrome Extension (Client-Side Telemetry Agent)**
2. **Desktop Tracker (Native Application Monitor)**
3. **FastAPI Backend (Processing & Persistence Layer)**
4. **React Dashboard (Visualization & Control Interface)**
5. **WebSocket Real-Time Communication Layer**

The architecture follows a hub-and-spoke model where the FastAPI backend serves as the central processing hub, receiving telemetry from both the Chrome extension and the desktop tracker, while broadcasting blocking rules and live updates to all connected clients via WebSocket.

### C. Data Flow Architecture

The data flow in POLARIS follows a three-phase pipeline:

**Phase 1: Telemetry Collection.** Both the Chrome extension and the desktop tracker independently collect activity data. The extension monitors browser tabs, scroll depth, focus state, and YouTube video metadata. The desktop tracker polls the Windows foreground window every `POLL_INTERVAL_SECONDS` (configurable, default: 5 seconds) using the Win32 API (`GetForegroundWindow`, `GetWindowThreadProcessId`).

**Phase 2: Privacy Filtering & Classification.** Before any data leaves the client, the privacy filter strips URLs to hostname-only format. The tracking service then applies a four-level classification cascade:
1. User-specific domain overrides (highest priority)
2. Global domain classifications
3. Default hardcoded category map (36 domains)
4. YouTube-specific three-tier cascade (NLP → keyword → domain default)

**Phase 3: Aggregation & Presentation.** The productivity service aggregates raw logs into daily summaries using a weighted scoring formula, and the dashboard presents these through real-time WebSocket updates and historical trend analysis.

## IV. METHODOLOGY

### A. Behavioral Telemetry Collection

#### 1) Browser-Based Tracking (Chrome Extension)

The Chrome extension implements a Manifest V3 service worker architecture with four specialized content scripts:

**Background Service Worker (`background.js`, 520 lines).** The service worker orchestrates all tracking logic. It uses `chrome.tabs.onActivated` and `chrome.tabs.onUpdated` listeners to detect tab switches, maintains a session state in `chrome.storage.local` to survive service worker sleep/wake cycles, and implements a 30-second heartbeat alarm (`chrome.alarms.create("heartbeat", { periodInMinutes: 0.5 })`) for:
- Flushing accumulated tracking data to the backend via REST API
- Sending WebSocket heartbeats to maintain connection
- Retrying offline-queued logs

**YouTube Intelligence (`youtubeTracker.js`, 321 lines).** This content script is injected exclusively on YouTube pages. It monitors the `ytd-watch-metadata` DOM element and the HTML5 video element to extract:
- Video title (from `yt-formatted-string.style-scope.ytd-watch-metadata`)
- Channel name (from `ytd-channel-name`)
- Current playback time (`video.currentTime`) — reported every 10 seconds
- Playback rate (`video.playbackRate`)
- Video duration (`video.duration`)

The tracker implements a keyword-based classification system with 95+ learning keywords organized into categories (General Education, CS/Programming, Web Fundamentals, Science & Math, Academic). When a video title matches any keyword, it is classified as "productive." When the backend matching service is available, the tracker upgrades to semantic NLP matching via the `/api/ai/match-video` endpoint.

**Scroll Tracker (`scrollTracker.js`, 94 lines).** Measures scroll depth as a percentage of total page height and computes scroll velocity (average pixels per scroll event). Reports are throttled to 5 events/second maximum using `setTimeout` debouncing, and aggregated data is sent to the background script every 30 seconds.

**Focus Tracker (`focusTracker.js`, 75 lines).** Monitors window focus state and page visibility using the Page Visibility API. Computes continuous focus duration and reports state changes to the background script. A 3-second polling fallback catches edge cases where event listeners miss state transitions.

#### 2) Desktop Application Tracking

The desktop tracker is a standalone Python application that monitors native Windows applications:

**Window Sampling.** Every `POLL_INTERVAL_SECONDS`, the tracker calls `win32gui.GetForegroundWindow()` to obtain the active window handle, then `win32process.GetWindowThreadProcessId()` to resolve the process ID, and finally `psutil.Process(pid).name()` to identify the executable.

**Idle Detection.** The tracker uses the Windows `GetLastInputInfo` API via `ctypes` to detect user idle periods. When idle time exceeds `IDLE_THRESHOLD_SECONDS` (configurable), the current session is flushed with `is_active=False`.

**Browser Deduplication.** The tracker maintains a curated set of 8 known browser executables (`chrome.exe`, `msedge.exe`, `firefox.exe`, `brave.exe`, `opera.exe`, `vivaldi.exe`, `safari.exe`, `arc.exe`). When the foreground process matches any of these, the tracker classifies it as "neutral" and skips detailed tracking, deferring to the Chrome extension.

**NLP Fallback for Unknown Applications.** When the static classifier returns "unknown" for a process, the tracker queries the backend's `/api/tracking/classify-app` endpoint, which uses the LLM (Llama-3.3-70B via Groq or GPT via OpenAI) to classify the application and window title into productive/distracting/neutral. The result is cached in `dynamic_cache` (in-memory dictionary) for the lifetime of the tracker process.

**Application Classification Database.** The classifier maintains three curated sets:
- `PRODUCTIVE_APPS`: 107+ executables (IDEs, terminals, design tools, databases)
- `DISTRACTING_APPS`: 80+ executables (games, social media, streaming)
- `NEUTRAL_APPS`: 60+ executables (browsers, system utilities, VPNs)

#### 3) Session Management and Offline Resilience

Both tracking agents implement offline resilience through queuing:

**Chrome Extension Offline Queue (`storage.js`).** When the backend is unreachable, tracking logs are buffered in `chrome.storage.local` under the `tracking_queue` key, with a maximum queue size of 500 entries. Each entry is timestamped with a `queued_at` field. On each heartbeat, the background script attempts to flush the queue via the `/api/tracking/batch` endpoint. The `queued_at` field is stripped before transmission to prevent Pydantic validation errors on the backend.

**Desktop Tracker Batch Flush.** The desktop tracker accumulates completed sessions in memory and flushes them to the backend every `FLUSH_INTERVAL_POLLS` polls (configurable). On shutdown (SIGINT/SIGTERM), remaining sessions are flushed synchronously.

### B. Content Classification Engine

POLARIS implements a hierarchical content classification system with three tiers:

#### 1) Domain-Level Classification

The tracking service maintains a hardcoded `DEFAULT_CATEGORIES` dictionary mapping 36 domains to three categories:
- **Productive** (16 domains): `github.com`, `stackoverflow.com`, `leetcode.com`, `coursera.org`, `udemy.com`, `notion.so`, `docs.google.com`, `kaggle.com`, etc.
- **Distracting** (13 domains): `youtube.com`, `reddit.com`, `twitter.com`, `instagram.com`, `tiktok.com`, `netflix.com`, etc.
- **Neutral**: All unlisted domains default to "neutral."

Classification priority follows a four-level cascade:
1. User-specific domain override (`DomainCategory` with `user_id`)
2. Global domain classification (`DomainCategory` with `is_global=True`)
3. Default hardcoded map
4. Partial domain match (e.g., `docs.python.org` matches `python.org`)

#### 2) YouTube Three-Tier Classification Cascade

For YouTube domains (`youtube.com`, `youtu.be`), POLARIS applies a specialized three-tier cascade:

**Tier 1 — Extension-Side NLP Classification (Highest Priority).** When the `yt_classification` field is present in the tracking log, the backend trusts it directly. This field is set by the YouTube tracker after semantic matching with study plan chapters via the `/api/ai/match-video` endpoint. The semantic matching uses all-MiniLM-L6-v2 embeddings and cosine similarity with thresholds: ≥0.75 for auto-match, ≥0.65 for candidate confirmation.

**Tier 2 — Server-Side Keyword Analysis (Fallback).** If NLP classification is unavailable and the video title is present, the `_is_learning_video()` function scans the title against 95+ learning keywords. A match reclassifies the video from "distracting" (the domain default) to "productive."

**Tier 3 — Domain Default (Baseline).** If neither NLP classification nor keyword analysis yields a result, the domain-level classification applies (`youtube.com` → "distracting").

#### 3) Semantic Video-to-Chapter Matching

The matching service (`matching_service.py`, 229 lines) implements the core NLP engine:

**Model Selection.** POLARIS uses the `all-MiniLM-L6-v2` model from the sentence-transformers library, producing 384-dimensional L2-normalized embeddings. The model is loaded once at application startup via `preload_model()` and cached as a singleton for the lifetime of the server process.

**Chapter Text Construction.** Each study plan chapter is converted to an embedding-ready text string by combining:
- Chapter title
- Chapter description (truncated to 300 characters)
- High-importance keywords (repeated 2x for keywords with importance ≥75) from the AI-generated `keyword_importance` dictionary

The `keyword_importance` dictionary assigns scores from 0–100:
- **80–100**: Core topic keywords (e.g., "fibonacci," "knapsack," "recursion")
- **40–70**: Context words (e.g., "introduction," "algorithm")
- **10–30**: Generic words (e.g., "tutorial," "lecture")
- **0–10**: Channel/creator names (e.g., "striver," "neetcode")

**Matching Algorithm.** When a YouTube video is detected, the extension calls `/api/ai/match-video` with the video title, URL, description, duration, and channel name. The backend:
1. Retrieves all user chapters with stored embeddings
2. Computes cosine similarity between the video embedding and each chapter embedding
3. Applies an incomplete-chapter tiebreaker bonus (+0.05) to prefer unfinished chapters when similarities are close
4. Returns the best match if it exceeds the `THRESHOLD_CONFIRM` (0.65)

**Threshold Design.**
- `THRESHOLD_MATCH` (0.75): Auto-assign — high confidence, no user intervention needed
- `THRESHOLD_CONFIRM` (0.65): Candidate — the system assigns but flags `needs_confirmation`
- Below 0.65: No match — the video is not associated with any chapter

### C. Productivity Scoring Algorithm

The productivity score is computed server-side in `productivity_service.py` using a weighted formula:

```
ProductivityScore = ((P × 1.0 + N × 0.3 − D × 0.5) / T) × 100 + QuizBonus
```

Where:
- `P` = productive seconds
- `N` = neutral seconds
- `D` = distracting seconds
- `T` = total active seconds (max(T, 1) to avoid division by zero)
- `QuizBonus` = quiz_average × 0.1 (capped at +10 points)

The score is clamped to the range [0, 100].

**Focus Factor** is computed as:
```
FocusFactor = (P + N) / max(T, 1)
```

This represents the fraction of browsing time spent on non-distracting content, ranging from 0.0 to 1.0.

**Trend Analysis.** The system computes trend direction by comparing the average score of the three most recent days against the average of the three earliest days in the window:
- If recent average > older average × 1.1 → "improving"
- If recent average < older average × 0.9 → "declining"
- Otherwise → "stable"

### D. Adaptive Learning Pipeline

#### 1) Study Plan Generation

POLARIS uses a unified API call to generate complete learning paths:

**Input Processing.** The user provides a learning goal (text), duration (days), and optionally a PDF syllabus document. The system computes an adaptive difficulty level based on the user's recent quiz history:
- Average score ≥ 80% → "hard"
- Average score < 50% → "easy"
- Otherwise → "medium"

**LLM Prompt Engineering.** The system constructs a detailed prompt requesting:
- `chapters_target` = max(duration_days, min(duration_days × 1.5, 18)) chapters
- `quiz_target` = max(8, min(20, duration_days × 2)) quiz questions
- Per-chapter: title, description, YouTube search query, duration estimate, key topics, keyword importance dictionary, and 1–2 coding tasks with starter code, test cases, hints, and solutions
- Daily schedule distributing chapters across the specified duration

**Learner Profile Injection.** If the user has prior study plan history, the `LearnerProfile` context is injected into the prompt with instructions to:
- Skip beginner chapters on already-mastered topics
- Add extra chapters on identified weak areas
- Calibrate quiz difficulty to past performance

**Robustness.** The system implements a three-level response parsing strategy:
1. Direct JSON parsing of the LLM response
2. Partial salvage via regex extraction of the `chapters` array from truncated JSON
3. Hard fallback with a minimal single-chapter plan

#### 2) Chapter Progress Tracking

Each study plan chapter is tracked via a `ChapterProgress` database row with the following lifecycle:

1. **Creation:** When a study plan is generated, a `ChapterProgress` row is created for each chapter with semantic embeddings pre-computed via batch encoding.

2. **Video Assignment:** When the user watches a YouTube video that matches a chapter (via semantic matching or manual "Search on YouTube" flow), the chapter's `youtube_url`, `youtube_title`, `video_duration_seconds`, and `creator_name` fields are populated.

3. **Progress Updates:** The YouTube tracker calls `/api/ai/study-plan/{id}/chapter/{n}/update-progress` every 10 seconds with the current `video.currentTime`, `video.duration`, and `playback_rate`.

4. **Auto-Completion:** A chapter is automatically marked complete when either:
   - The `video.ended` event fires, OR
   - The watched percentage reaches ≥95% of video duration

5. **AI Summary Generation:** Upon completion, a background task calls `generate_chapter_summary()` to produce a 4–6 bullet-point summary of key concepts covered.

6. **Quiz Gating:** The quiz for a study plan is locked until all chapters are marked complete.

#### 3) Quiz and Assessment Engine

**Generation.** Quizzes are generated as part of the study plan in a single LLM call, containing:
- 5 multiple-choice questions (MCQ) with 4 options each
- 2 conceptual questions with rubrics
- 1 coding problem (if topic involves programming)

**Submission and Grading.** MCQ answers are auto-graded by comparing `user_answer` indices against `correct_answer` indices. The score is computed as `(correct / total) × 100`.

**Retake Policy.** The system enforces:
- Maximum 3 attempts per plan
- 24-hour cooldown between attempts after maximum is reached

**Agent Analysis.** After quiz submission, the `/api/ai/study-plan/{plan_id}/analyze-quiz` endpoint performs LLM-powered analysis:
- Identifies wrong answers and extracts weak topics
- Considers quiz score trend across attempts
- Evaluates watch statistics (playback speed, completion rates)
- Recommends extra study days and difficulty adjustments
- All recommendations require manual user approval

#### 4) Learner Profile and Cross-Plan Personalization

The `LearnerProfile` model maintains:
- `mastered_topics`: Chapter titles from plans where quiz score ≥ 60% (last 50 entries)
- `weak_plan_topics`: Plan titles where score < 60% (last 10 entries, removed on improvement)
- `avg_quiz_score`: Rolling average across all quiz attempts
- `completed_plans`: Array of `{title, score, chapters}` (last 20 entries)

This profile is injected into subsequent study plan generation prompts, enabling the system to:
- Skip redundant introductory content on mastered topics
- Allocate extra chapters for identified weak areas
- Adjust quiz question depth based on historical performance patterns

### E. Distraction Blocking Mechanism

POLARIS implements a multi-layer blocking system:

#### 1) Network-Level Blocking (Hard Mode)

The extension uses the `declarativeNetRequest` API to block domains at the network layer:
- Dynamic rules are created with `chrome.declarativeNetRequest.updateDynamicRules()`
- Rule IDs are generated via a hash function with a 1000 offset to avoid static rule conflicts
- Rules block all resource types: `main_frame`, `sub_frame`, `stylesheet`, `script`, `image`, `font`, `object`, `xmlhttprequest`, `ping`, `media`, `websocket`, `other`

#### 2) Visual Overlay Blocking (Soft Mode)

The block overlay (`blockOverlay.js`, 305 lines) provides a visual block for sites classified as distracting:

**Shadow DOM Isolation.** The overlay creates a `<div>` with `id="lifeos-portal"`, attaches a Shadow DOM (`attachShadow({ mode: 'open' })`), and renders the block UI within the shadow root. This prevents page CSS from interfering with the overlay and makes it harder for users to modify via browser developer tools.

**Anti-Removal Protection.** A `MutationObserver` watches the document root for child removals. If the overlay container is removed, it is immediately re-attached.

**Video Pause Loop.** A 500ms interval queries all `<video>` elements on the page and pauses any that are playing, preventing audio/video content from playing behind the overlay.

**YouTube-Specific Logic.** The overlay implements fine-grained YouTube blocking:
- Watch pages (`/watch`): Block only if `yt_current_classification === 'distracting'`
- YouTube home/search: Never auto-block (only block if manually/parentally blocked)
- Productive videos override even manual blocks: `finalBlocked = false` when classification is "productive"

#### 3) Blocking Rule Synchronization

Blocking rules are synchronized between the backend and extension via WebSocket:
- On WebSocket connection, the backend sends the full blocked domain list (`blocked_list_sync`)
- On parent block/unblock actions, the backend emits `site_blocked` or `site_unblocked` events
- The extension's `syncBlockedDomains()` function performs a diff sync: adds missing blocks and removes stale ones

### F. Ethical Parental Control

#### 1) Parent-Child Linking

POLARIS supports two linking mechanisms:

**Invite Code System.** Parents generate a random 8-character alphanumeric invite code, which the student enters to accept the connection. Both parties must have registered accounts with appropriate roles ("parent" or "student").

**OTP-Based Verification.** The `ParentChildConnection` model implements a 4-digit OTP-based verification system with time-limited access (30-day expiration). The OTP must be verified before the connection becomes "active."

#### 2) Privacy-Preserving Analytics

The `get_child_overview()` function explicitly limits the data exposed to parents:
- ✅ Productivity scores, focus factors, total active minutes
- ✅ Domain-level time breakdowns (e.g., "youtube.com: 45 min")
- ✅ Blocked site management
- ❌ Video titles (filtered from output)
- ❌ Search queries (never stored)
- ❌ Chat content (sensitive domains blocklisted)

### G. Polaris Lab: Integrated Coding Environment

#### 1) Task Generation

Coding tasks are generated alongside study plan chapters in the same LLM call. Each task includes:
- Title and description
- Difficulty level (easy/medium/hard)
- Programming language (Python or JavaScript)
- Starter code with function signature
- 2+ test cases with input/expected output
- 1–2 hints
- Reference solution

Tasks are persisted in the `CodingTask` model with foreign keys to `study_plan_id` and `chapter_number`.

#### 2) Code Execution Sandbox

The Lab supports three execution modes:

**Python (Server-Side Sandbox).** User code is executed in an isolated subprocess with:
- 10-second timeout
- No network access
- No filesystem access
- Restricted imports

**JavaScript (Client-Side).** JavaScript code is executed directly in the browser within the Lab page, using `eval()` in a controlled context.

**HTML/CSS (Live Preview).** HTML/CSS code is rendered in an embedded `<iframe>` for live visual preview.

#### 3) Automated Verification

The code verifier runs user code against task test cases:
- For each test case, it compares actual output against expected output
- Results include per-test-case pass/fail status, actual vs. expected values
- A score from 0–100 is computed based on the ratio of passed tests
- Submissions are persisted in the `CodingSubmission` model

### H. Real-Time Communication Architecture

#### 1) WebSocket Protocol

POLARIS implements a custom WebSocket protocol with the following message types:

| Message Type | Direction | Purpose |
|---|---|---|
| `heartbeat` | Client → Server | Keep-alive signal |
| `heartbeat_ack` | Server → Client | Heartbeat acknowledgment |
| `sync_blocked` | Client → Server | Request blocked domain list |
| `blocked_list_sync` | Server → Client | Full blocked domain list |
| `site_blocked` | Server → Client | Single domain blocked |
| `site_unblocked` | Server → Client | Single domain unblocked |
| `live_activity` | Client → Server | Real-time browsing data |
| `live_tracking` | Server → Client | Relayed live browsing data |
| `focus_session_start` | Server → Client | Focus session activation |
| `focus_session_stop` | Server → Client | Focus session deactivation |
| `productivity_update` | Server → Client | Score update notification |

#### 2) Connection Management

The `ConnectionManager` class supports multiple simultaneous connections per user (multi-tab/multi-device). It maintains a `Dict[str, Set[WebSocket]]` mapping and uses `asyncio.Lock` for thread-safe access. Dead connections are automatically cleaned up after failed send attempts.

#### 3) Authentication

WebSocket connections are authenticated via JWT token passed as a query parameter (`?token=<JWT>`). The token is validated using the same `decode_token()` function used for REST API authentication.

### I. Focus Session System

The Focus Session feature provides time-boxed distraction blocking:

**Activation.** The user selects a duration (1–180 minutes) from the dashboard. The backend sends a `focus_session_start` WebSocket event containing:
- Duration in minutes
- Preset label (e.g., "25 min" for Pomodoro)
- List of distracting domains to block during the session
- `youtube_allowed_for_learning: true` flag (ensures educational YouTube content remains accessible)

**Default Blocked Domains.** During focus sessions, the following domains are automatically blocked: `instagram.com`, `facebook.com`, `twitter.com`, `x.com`, `tiktok.com`, `reddit.com`, `twitch.tv`, `netflix.com`, `youtube.com/shorts`. Main YouTube is explicitly kept unblocked for educational watching.

**Deactivation.** The backend sends a `focus_session_stop` event, restoring the user's default blocking configuration.

### D. Database Migration Strategy

The application implements an in-code migration system during the FastAPI lifespan startup:
1. `ALTER TABLE tracking_logs ADD COLUMN page_title VARCHAR(500) NULL`
2. `ALTER TABLE chapter_progress ADD COLUMN keyword_importance JSON NULL`
3. `ALTER TABLE chapter_progress ADD COLUMN chapter_embedding JSON NULL`
4. `ALTER TABLE chapter_progress ADD COLUMN playback_rate FLOAT DEFAULT 1.0`
5. `ALTER TABLE chapter_progress ADD COLUMN ai_summary TEXT NULL`

Each migration is guarded by a column existence check using SQLAlchemy's `inspect` module, ensuring idempotency.

### E. Embedding Backfill

At startup, the system runs a background task (`_backfill_chapter_embeddings()`) that:
1. Queries all `ChapterProgress` rows where `chapter_embedding IS NULL`
2. Generates embeddings using `build_chapter_text()` → `embed_text()`
3. Stores embeddings as JSON arrays in the `chapter_embedding` column

This ensures backward compatibility when the embedding feature is added to an existing deployment.

## VI. PROPOSED EVALUATION METHODOLOGY

> **Note:** The following evaluation methodology is proposed for future work. No experimental results have been collected or fabricated at this time. All metrics described below are evaluation designs, not empirical findings.

### A. Evaluation Dimensions

The evaluation of POLARIS should be conducted across four dimensions:

#### 1) Classification Accuracy

**YouTube Content Classification.** A test corpus of 500 YouTube videos (250 educational, 250 entertainment) should be assembled from diverse categories. Each video should be labeled by three human annotators, with inter-annotator agreement measured via Cohen's κ. The semantic matching engine should be evaluated on:
- **Precision**: Fraction of videos classified as "productive" that are truly educational
- **Recall**: Fraction of truly educational videos that the system correctly identifies
- **F1 Score**: Harmonic mean of precision and recall

Three classification strategies should be compared:
- Domain-only baseline (all YouTube → distracting)
- Keyword-based classification (95 keywords)
- Semantic embedding classification (all-MiniLM-L6-v2)

**Desktop Application Classification.** The NLP fallback classifier should be evaluated on a corpus of 100 unknown applications with human-labeled categories.

#### 2) Tracking Accuracy

**Browser Tracking.** The accuracy of tab-switch counting, duration measurement, and scroll depth calculation should be validated against manual observation logs.

**Desktop Tracking.** The deduplication protocol should be verified: when a user switches between Chrome and VS Code, the system should produce exactly one tracking entry per activity window, with no gaps or overlaps.

**Offline Resilience.** The offline queue should be tested by:
1. Disconnecting network connectivity during tracking
2. Accumulating 50+ tracking entries in the queue
3. Reconnecting and verifying that all entries are correctly flushed

#### 3) Learning Outcome Metrics

**Study Plan Quality.** Generated study plans should be evaluated by domain experts on:
- Chapter coverage relative to the stated goal
- Quality and relevance of YouTube search queries
- Difficulty progression across chapters
- Quiz question quality and answer accuracy

**Adaptive Difficulty.** The system's ability to adjust quiz difficulty based on prior performance should be measured:
- Does a student with avg score ≥80% receive "hard" questions?
- Does a student with avg score <50% receive "easy" questions?
- Do subsequent plans for the same user skip mastered topics?

#### 4) System Performance

**Latency.** End-to-end latency for critical paths should be measured:
- Tracking log ingestion (target: <200ms)
- Semantic video matching (target: <500ms)
- Study plan generation (target: <30s)
- WebSocket blocking rule propagation (target: <100ms)

**Embedding Throughput.** The batch embedding generation throughput for chapter backfill should be measured in chapters/second.

**Resource Consumption.** The Chrome extension's impact on browser performance should be measured:
- CPU usage during active tracking
- Memory footprint of the service worker
- Battery impact on laptop devices

### B. Ethical Evaluation

The parental control module should be evaluated through:
- **Information Leakage Audit**: Systematic verification that no sensitive data (search queries, video titles, chat content) is exposed through any parental API endpoint
- **Autonomy Preservation**: Assessment of whether the system's transparency features (notifications, visible blocking overlays) maintain adolescent agency
- **Privacy Filter Verification**: Automated testing that no full URLs are stored in the database

## VII. DISCUSSION

### A. Threats to Validity

**Internal Validity.** The semantic matching thresholds (0.75 and 0.65) were selected based on empirical observation during development rather than systematic optimization. A formal threshold calibration study using ROC analysis would provide more rigorous threshold selection.

**External Validity.** The system has been designed and tested primarily in a computer science education context. The keyword database and classification models may not generalize well to other academic disciplines (e.g., humanities, social sciences).

**Construct Validity.** The productivity score formula assigns fixed weights (productive=1.0, neutral=0.3, distracting=-0.5) that may not accurately reflect the true productivity value of different activities. For example, reading documentation (productive) and writing code in an IDE (also productive) may contribute differently to actual learning outcomes.

### B. Limitations

1. **Platform Dependency.** The desktop tracker is Windows-only (requires `pywin32`, `ctypes` calls to `user32.dll`). macOS and Linux support would require platform-specific implementations.

2. **Browser Dependency.** The Chrome extension uses Chrome-specific APIs (`chrome.declarativeNetRequest`, `chrome.idle`, `chrome.alarms`). Firefox and Safari support would require API adaptation.

3. **LLM Dependency.** Study plan and quiz generation depend on external LLM providers (Groq/OpenAI). Service outages, rate limits, or API changes could impact functionality. The partial salvage mechanism and hard fallback mitigate this partially.

4. **Single-Language NLP.** The all-MiniLM-L6-v2 model is optimized for English text. Content in other languages may receive lower-quality embeddings, reducing classification accuracy.

5. **Manual Keyword Maintenance.** The 95+ learning keywords in the fallback classifier require manual curation. Emerging educational topics (e.g., new programming languages) would not be classified until keywords are added.

### C. Ethical Considerations

**Surveillance vs. Guidance.** POLARIS explicitly positions itself as a guidance tool rather than a surveillance system. The design choices—showing overlay notifications, providing transparent blocking reasons, and restricting parental access to aggregate metrics—are intentional ethical guardrails.

**Data Minimization.** The privacy filter strips URLs to hostnames before storage, and the sensitive domain blocklist prevents tracking on communication platforms. This represents a deliberate trade-off: the system sacrifices fine-grained analytics (e.g., "which specific Reddit post was viewed") in favor of privacy preservation.

**Consent and Transparency.** The blocking overlay explicitly states the reason for blocking ("This video is classified as distracting" / "This site is classified as distracting") and provides a clear exit mechanism ("Return to Home" / "Go Back to Work").

## VIII. CONCLUSION AND FUTURE WORK

### A. Conclusion

This paper presented POLARIS, a hybrid AI-powered platform that unifies digital well-being monitoring, adaptive learning orchestration, and ethical parental oversight. The system's key innovation lies in its semantic content classification engine, which uses sentence-transformer embeddings to distinguish educational from entertainment content at the individual video level—a capability absent from existing domain-level classification systems. The dual-layer tracking architecture, encompassing both browser extension and desktop tracker with explicit deduplication, provides comprehensive behavioral telemetry without the double-counting that plagues hybrid monitoring approaches.

The adaptive learning pipeline demonstrates a novel approach to external content curation: rather than creating proprietary educational content, POLARIS builds personalized curricula around existing YouTube educational videos, automatically tracking watch progress and gating assessments behind verified completion. The cross-plan LearnerProfile ensures that each successive study plan builds upon prior knowledge, avoiding redundant instruction.

The ethical parental control module demonstrates that meaningful oversight is possible without surveillance: parents receive aggregate productivity metrics and domain-level time breakdowns without access to individual video titles, search queries, or chat content. The privacy-first data architecture, with dual-layer URL stripping and sensitive domain filtering, provides a concrete implementation of the data minimization principle.

### B. Future Work

1. **Multi-Platform Desktop Tracking.** Extending the desktop tracker to macOS (using AppKit/NSWorkspace) and Linux (using X11/Wayland window managers) would broaden the system's applicability.

2. **Cross-Browser Extension Support.** Porting the extension to Firefox (WebExtensions API) and Safari (Safari Web Extensions) would increase the user base.

3. **Fine-Tuned Classification Models.** Fine-tuning the all-MiniLM-L6-v2 model on a labeled dataset of educational vs. entertainment video titles could improve classification accuracy beyond the current general-purpose performance.

4. **Federated Learning for Classification.** Implementing federated learning would allow the classification model to improve from aggregate user feedback without centralizing individual browsing data.

5. **Multi-Modal Content Analysis.** Incorporating video thumbnail analysis (computer vision) and audio transcript analysis (speech-to-text) could provide additional classification signals beyond title text alone.

6. **Gamification Mechanics.** The existing streak system and skill tree provide basic gamification. Future work could implement experience points, achievement badges, and competitive leaderboards to increase engagement.

7. **Spaced Repetition Integration.** Integrating the quiz engine with a spaced repetition algorithm (e.g., SM-2) could optimize long-term knowledge retention.

8. **Calendar and External Integration.** The existing Google Calendar OAuth integration schema (present in the codebase but not fully implemented) could be extended to sync study sessions and deadlines with external calendar applications.

9. **Mobile Application.** A companion mobile application could extend tracking to mobile device usage, providing a complete picture of digital behavior across all platforms.

10. **Empirical Evaluation.** A controlled study with student participants, measuring actual academic outcomes (grades, test scores) correlated with POLARIS usage patterns, would provide rigorous evidence of the system's educational impact.

## APPENDIX B: PRODUCTIVITY SCORING MATHEMATICAL FORMULATION

### B1. Variables

Let:
- $T_{p}$ = total productive seconds in the evaluation period
- $T_{n}$ = total neutral seconds
- $T_{d}$ = total distracting seconds
- $T_{total} = T_{p} + T_{n} + T_{d}$ (total active seconds)
- $Q_{avg}$ = average quiz score for the evaluation period (0–100)
- $w_{p} = 1.0$ (productive weight)
- $w_{n} = 0.3$ (neutral weight)
- $w_{d} = -0.5$ (distracting penalty)
- $k_{q} = 0.1$ (quiz bonus coefficient)

### B2. Productivity Score

$$S = \min\left(100, \max\left(0, \frac{T_{p} \cdot w_{p} + T_{n} \cdot w_{n} + T_{d} \cdot w_{d}}{\max(T_{total}, 1)} \times 100 + Q_{avg} \cdot k_{q}\right)\right)$$

### B3. Focus Factor

$$F = \frac{T_{p} + T_{n}}{\max(T_{total}, 1)}$$

### B4. Trend Direction

Given daily scores $S_1, S_2, \ldots, S_n$ ordered chronologically:

$$\bar{S}_{recent} = \frac{1}{3}\sum_{i=n-2}^{n} S_i, \quad \bar{S}_{older} = \frac{1}{3}\sum_{i=1}^{3} S_i$$

$$\text{Trend} = \begin{cases} \text{improving} & \text{if } \bar{S}_{recent} > 1.1 \cdot \bar{S}_{older} \\ \text{declining} & \text{if } \bar{S}_{recent} < 0.9 \cdot \bar{S}_{older} \\ \text{stable} & \text{otherwise} \end{cases}$$

## APPENDIX C: SEMANTIC MATCHING THRESHOLD ANALYSIS

### C1. Cosine Similarity Distribution

For two L2-normalized vectors $\mathbf{a}$ and $\mathbf{b}$ produced by all-MiniLM-L6-v2:

$$\text{sim}(\mathbf{a}, \mathbf{b}) = \mathbf{a} \cdot \mathbf{b} = \sum_{i=1}^{384} a_i \cdot b_i$$

Since the vectors are L2-normalized, the dot product equals the cosine similarity, and the result lies in $[-1, 1]$.

### C2. Threshold Selection Rationale

The thresholds were selected based on the following design criteria:

- **THRESHOLD_MATCH (0.75):** At this similarity level, the chapter and video titles share substantial semantic overlap. Example: chapter "Dynamic Programming Introduction" matching video "Dynamic Programming Tutorial for Beginners" (expected similarity: ~0.82).

- **THRESHOLD_CONFIRM (0.65):** At this level, there is meaningful semantic relationship but potential for false positives. Example: chapter "Binary Search Trees" matching video "Tree Traversal Algorithms" (expected similarity: ~0.68). The system assigns the match but flags `needs_confirmation`.

- **Below 0.65:** Insufficient semantic similarity. Example: chapter "Neural Network Basics" matching video "How to Build a PC" (expected similarity: ~0.15).

### C3. Tiebreaker Logic

When multiple chapters exceed the confirmation threshold, the system applies a tiebreaker:

$$\text{score}(c) = \text{sim}(c) + \begin{cases} 0.05 & \text{if } c \text{ is incomplete} \\ 0.00 & \text{if } c \text{ is completed} \end{cases}$$

This small bonus ensures that incomplete chapters are preferred over completed ones when similarity scores are close, directing new videos toward chapters that still need progress.

## APPENDIX D: PRIVACY ARCHITECTURE

### D1. Client-Side Privacy Filter (`privacyFilter.js`)

**URL Sanitization Pipeline:**
1. Parse URL using `new URL(rawUrl)`
2. Extract `hostname` (lowercase, trimmed)
3. Strip `www.` prefix
4. Validate against hostname regex: `/^[a-zA-Z0-9][a-zA-Z0-9\-\.]*\.[a-zA-Z]{2,}$/`
5. Return clean hostname or empty string

**Field Sanitization:**
- `domain`: Capped at 255 characters
- `page_title`: Capped at 500 characters
- `yt_classification`: Capped at 20 characters
- `duration_seconds`: Floor to non-negative integer
- `tab_switches`: Floor to non-negative integer
- `scroll_depth`: Clamp to [0.0, 1.0]
- `is_active`: Coerce to boolean (default: true)

### D2. Server-Side Privacy Filter (`privacy.py`)

**Sensitive Domain Blocklist:**
```
mail.google.com, outlook.live.com, web.whatsapp.com,
messages.google.com, discord.com, slack.com
```

Tracking logs from these domains have their page titles redacted and are stored with hostname-only identifiers.

### D3. Data Never Stored

The following data categories are explicitly excluded from storage at all architectural layers:

- Full URLs (including paths, query parameters, and fragments)
- Search queries (Google, YouTube, Bing, etc.)
- Form input data
- Cookie values
- Authentication tokens (other than the user's own JWT)
- Email content
- Chat messages
- Private browsing/incognito activity (extension is disabled in incognito by default)
